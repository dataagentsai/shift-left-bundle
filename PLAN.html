Shift-Left Bundle

A light bundle that makes PySpark, Python and Databricks SQL code fail fast, before it runs. It reports cost, security, vulnerability, test and complexity problems, plus what a repo is missing. It is spec-driven like the Data Engineering and Agent Harness families: the checks name no product, and Databricks, then Azure, are bindings.

Working name, started 2 Nov 2026. Status: plan and reuse check done; decisions D1–D8 agreed as recommended on 2 Nov 2026. Spec 0.2 done 2 Nov 2026: 131 checks in 13 families, covering Python, PySpark, notebooks, SQL, dbt, materialized views and metric views (catalog/INDEX.md). Tier 2 done 2 Nov: a sample shop with 101 planted problems and 16 traps; Ruff alone catches 17 (tests/RESULTS.md). Next: Tier 3, the runner.

1. Lesson: what "shift left" means

Draw a line of the life of a change from left to right. A problem costs more the further right it is found. A cartesian join caught in the editor costs one minute. Caught on the cluster, it costs a failed job, a bill and a morning.

What it can catch: code shapes that are always wrong or costly (collect in a loop, SELECT *, cross join, DELETE without WHERE), secrets, known-vulnerable libraries, unsafe code, untested logic, overly complex functions, a bad query plan on empty tables, and costly job and cluster settings.

What it can't catch: data skew, real data volumes, flaky sources, or what the cluster actually costs at run time. Those need the app to run (CostLens post-run, the simulator, integration tests). The bundle is one part of testing and code review, not all of it.

None of this is new. The ideas below are standard, and each comes with mature open-source tools. The bundle combines them for data code.

5. Reuse: what we take, what we build

Do we need SonarQube?

No. Verdict: Drop.

It needs a server and a database, pull-request analysis is in the paid editions, and it knows nothing about Spark cost or Databricks. What Sonar gives (rules, a dashboard, "clean as you code") we get lighter: Ruff and Opengrep for rules, SARIF shown on the pull request for the dashboard, and diff-cover plus a baseline for "clean as you code". 6. What the reports look like (illustrative, not measured)

Purity, tests and complexity

For PySpark, a function counts as pure when it takes DataFrames and values in and returns a DataFrame, with no reads, writes, dbutils, global spark, clock, random or env vars. Pure functions get unit tests on tiny DataFrames.

Can PySpark code be pure? Yes, for most of the logic

Spark makes this easier than plain Python. A DataFrame never changes in place: every step returns a new DataFrame, and nothing runs until an action such as a write. So a function that takes a DataFrame and returns a DataFrame using only column expressions is pure. Same input, same output, nothing touched outside. Spark even has df.transform(f) to chain such functions.

# Before: impure. It reads a table, uses the clock and writes, so a test needs real tables.
def load_silver_orders():
    df = spark.table("bronze.orders")
    df = df.dropDuplicates(["order_id"]).withColumn("load_ts", F.lit(datetime.now()))
    df.write.mode("append").saveAsTable("silver.orders")

# After: the logic is pure; the read, clock and write sit in a thin shell.
def clean_orders(orders: DataFrame, load_ts: datetime) -> DataFrame:      # pure: unit test this
    return orders.dropDuplicates(["order_id"]).withColumn("load_ts", F.lit(load_ts))

def run(spark):                                                          # impure shell: integration test
    clean_orders(spark.table("bronze.orders"), datetime.now()).write.mode("append").saveAsTable("silver.orders")

The unit test builds a three-row DataFrame on a local Spark session and compares the result with assertDataFrameEqual. It runs in seconds with no cluster, written as one table of cases (input rows, expected rows).

What stays impure, on purpose: reads, writes, MERGE, dbutils, and job entry points. These should be thin. For a MERGE, the "what to merge" logic (dedupe, SCD2 rows) is pure and only the final MERGE call is not. Values like current_timestamp(), rand() and uuid() make a function non-repeatable, so pass them in as parameters. Also keep actions like .count() and .collect() out of pure functions, because they make Spark run and cost money. In a Declarative Pipelines table function, the decorated function stays a one-line call to a pure function.

How do we know a function is pure?

We read its syntax tree and look for anything that touches the world outside it. Python is too dynamic to prove purity in every case, so the report gives three answers instead of two:

VerdictMeaningExample
impureFound a side effect. The report gives the reason and the line.spark.table, .write, saveAsTable, DeltaTable.merge, dbutils, open, HTTP calls, os.environ, datetime.now, random, F.current_timestamp() / rand() / uuid(), global spark, changing an argument or a global, actions like .collect() / .count() / .show()
pureEvery call is on a known-pure list and nothing else is touched.DataFrame methods that return a new DataFrame (select, withColumn, filter, join, groupBy().agg, dropDuplicates, union), most of pyspark.sql.functions, math, re, and other functions in the repo already found pure
unknownIt calls something we can't see into (a library not on either list, a function passed in as an argument, getattr tricks). Counted as not pure until someone marks it.some_lib.enrich(df)
  • It follows calls. If clean_orders calls a helper that reads a table, clean_orders is impure too, and the report shows the chain.
  • Marking. A developer can mark a function @pure (deal's marker). The static check still runs, so a wrong mark is reported.
  • Proof at test time. A pytest fixture makes Spark's read, write and catalog calls fail during unit tests of pure functions. If a "pure" function touches a table, its test fails. Each test also runs the function twice and checks that both outputs match.
  • Measured, not claimed. The sample repo has planted pure, impure and tricky functions with a hidden answer key, so we report how often the verdict is right.

Build on, not from scratch: Python's ast for the tree, deal's list of generic side effects, and our Spark lists (reads, writes, actions, non-repeatable functions). CostLens already holds most of those Spark lists in code_structure.py.

Coverage: coverage.py (run through pytest-cov) measures Python and PySpark the same way, because PySpark code is Python running on the driver. It has three blind spots. Code inside Python UDFs runs in worker processes and needs extra setup to be counted. SQL text has no line coverage at all, so SQL is covered by tests that check its output. Notebooks are hard to measure, so the logic belongs in .py modules that thin notebooks import. The purity rule fixes all three: logic sits in pure functions in modules, where coverage works.

7. Design: spec, binding, ports

Same shape as the AI and DE families, and code-to-interface throughout.

catalog/        the spec: checks/*.yaml (id, family, why, stage, gate, dac: [COST-02 …])  ← no product names
bindings/       databricks.yaml, azure.yaml: check id → tool + its rule id + config     ← only place for product names
runner/         ports: Scanner, PlanSource, Reporter, Gate, Baseline
                adapters: ruff, opengrep, sqlfluff, costlens, gitleaks, pip-audit, coverage,
                          complexipy, purity, repo-review, scorecard      (one adapter per tool)
                output: findings.sarif (our ids) + REVIEW.md
templates/      .pre-commit-config.yaml, CI snippets (GitHub Actions, Azure DevOps)
examples/       sample-project with planted problems; tests/answer-key.yaml
skills/         a Claude skill that reads REVIEW.md and proposes fixes (LLM only after the deterministic run)

Git structure

Our repo: one repo now, holding the spec, bindings, runner and sample together. Split the catalog into its own repo only when the Azure binding lands and the checks are stable (the same rule DAC follows).

Links to other repos, all pinned by version: costlens-core as a package (cost adapter); DAC ids from data-platform-catalog (each check has dac:). data-project-review checks a project's documents, and this bundle checks its code, so they are siblings with shared ids where they overlap.

A client repo using it splits the checks by speed:

WhereRunsTime budget
Laptop, on commit (pre-commit)Ruff (lint, clean code, security), SQL lint, gitleaks, CostLens code + SQL rules, bundle rules, on changed files only< 10 s
Pull request (required check, main is protected)everything above on the whole change + unit tests, diff coverage, purity, complexity, pip-audit, empty-table plan check, SARIF on the PR< 5 min
Nightly on mainmutation testing on pure functions, Scorecard, gap report, trend of scoresno limit
Before deploydatabricks bundle validate + config cost rules< 1 min

Branching: short-lived branches into a protected main, pull requests required, the bundle's PR job a required status check. Versions of the bundle are git tags; client repos pin a tag, so a new rule never breaks them by surprise.

Rule: deterministic first. Every check is a tool or a script. An LLM is used only to explain findings or draft a refactor of an impure function, and never decides pass or fail.
